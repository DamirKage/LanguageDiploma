# Персонализация: рекомендации и интервальное повторение

## Общая схема

```
данные MongoDB ──► buildSnapshot() ──► LearnerSnapshot ──► recommend() ──► RecommendationResult ──► composePlan() ──► план дня
                     (service.ts)        (чистые данные)     (engine.ts)                               (plan.ts)
```

`recommend()` — чистая детерминированная функция. Она не обращается к базе данных и времени системы, поэтому её можно тестировать модульно, запускать в симуляции и заменить обученной моделью с той же сигнатурой. Версия движка (`ENGINE_VERSION`) сохраняется в каждом снимке рекомендаций (`recommendationsnapshots`).

## Входные данные (LearnerSnapshot)

| Сигнал | Источник | Как используется |
|---|---|---|
| Точность по темам | `answerevents`, только первые попытки; «почти верно» = 0,7 | Слабые темы, снижение результатов |
| Текущая точность | последние 12 ответов по теме (`recentWindow`) | Замечает улучшение, а не только историю |
| Результаты по сессиям | точность по теме в каждой попытке (≥ 2 ответов) | Признак падения результатов |
| Частые категории ошибок | ошибки по теме за 30 дней | Причина «повторяются ошибки категории …» |
| Прогресс уроков | `lessonprogresses` (в т. ч. `completedAt` — дата первого прохождения) | Следующий урок, повторное прохождение, давление прогресса |
| Незавершённые попытки | `attempts` со статусом `in_progress` | «Продолжить» |
| Итоговые тесты | завершённые попытки `kind=test` | Тест модуля, переход на уровень |
| Повторение слов | `reviewitems`, `reviewlogs` | Нагрузка, просрочка, удержание за 30 дней |
| Регулярность | `users.lastActiveAt` | Возвращение после перерыва |
| Недавняя точность | последние 30 ответов | Целевая сложность заданий |
| Цели и бюджет времени | профиль | Совпадение с целью, план дня |
| Игнорирование | снимки за 7 дней, кроме сегодняшнего | Мягкое снижение балла |

## Кандидаты и признаки

Каждый признак нормирован в [0, 1]. Балл кандидата:

```
score = prior[type] + w_need·need + w_urgency·urgency + w_progress·progress
      + w_momentum·momentum + w_trend·trend + w_goal·goal − w_fatigue·min(3, ignored)
```

Веса по умолчанию (`config.ts`): need 1.0, urgency 0.9, progress 0.7, momentum 0.8, trend 0.35, goal 0.15, fatigue 0.08.

| Тип | Условие | Признаки |
|---|---|---|
| `placement` | уровень не определён и нет прогресса | progress = 1, prior 1.5 |
| `resume` | есть начатая попытка не старше 14 дней | momentum = (0,5 + 0,5·доля выполненного)·свежесть |
| `review` | есть слова к повторению | urgency = 0,5·min(1, нагрузка/20) + 0,3·min(1, просрочка/7) + 0,2·перерыв; need при удержании < 80% |
| `weak_topic` | сглаженная текущая точность < 0,7 или падение ≥ 15 п. п. | need = clamp((0,85 − M)/0,4), где M — оценка освоения с учётом забывания; trend, urgency = 0,5·min(1, дни/14), goal; prior 0,15 |
| `topic_refresh` | точность была в норме, но M < 0,7 или тема не встречалась ≥ 10 дней | need = clamp((0,85 − M)/0,4), urgency = 0,5·(1 − удержание), goal; prior 0,15 |
| `next_lesson` | первый непройденный урок пути, начиная с уровня учащегося | progress: 1 (1,2 при повышенной сложности) × (1 − 0,6·need самой слабой темы); не выше 0,55 при сниженной сложности и наличии слабых тем; ×0,8 после перерыва. urgency = 0,5·давление прогресса |
| `retry_lesson` | лучший результат урока < 70% | need = clamp((70 − лучший)/50 + 0,2) |
| `module_test` | все уроки модуля пройдены, тест не сдан | progress 0,8 (need 0,3 при пересдаче), оба × (1 − 0,6·need самой слабой темы модуля) |
| `level_up` | пройдены все уроки и тесты уровня | progress 1 |

Точность сглаживается байесовски: `(верно + 0,75·3) / (ответов + 3)`. При малом числе ответов оценка тянется к априорным 75%. Тема не считается слабой, пока по ней нет минимум 4 ответов (`minEvidence`). Так система разделяет наблюдаемые данные и оценки и не делает выводов по 1–2 ответам.

После ранжирования действуют ограничения разнообразия: не больше 2 слабых тем и 2 «освежающих» практик, по одному кандидату остальных типов (до 2 продолжений), всего не больше 6 рекомендаций.

### Оценка освоения с учётом забывания (rules-1.4)

Наблюдаемая точность описывает тему на момент последних ответов. Если тема давно не встречалась, она могла забыться, а сама оценка устарела. Поэтому движок использует оценку освоения

```
M = floor + (A − floor) · 2^(−max(0, дни − grace) / halfLife),   если A > floor;   иначе M = A
```

где A — сглаженная текущая точность, `дни` — дни с последней практики темы. Параметры (`config.forgetting`): halfLife = 7 дней, grace = 1 день, floor = 0,4. По M считается признак `need` и у слабых, и у «освежаемых» тем, так что давно не практиковавшаяся тема конкурирует со слабой на одной шкале. Классификация типа при этом опирается на наблюдения: `weak_topic` — точность реально низкая (причина `low_topic_accuracy`), `topic_refresh` — точность была в норме, но прошло много времени (причина `not_practiced_recently`). Период полураспада 7 дней консервативен: он включает и забывание, и рост неопределённости устаревшей оценки. Влияние параметра показано в абляции в `evaluation-results.md`.

### Порог освоения и давление прогресса (rules-1.4)

- **Порог освоения** (`remedialGate` = 0,6). Признак `progress` следующего урока умножается на (1 − 0,6·need), где need берётся по самой слабой теме с низкой или падающей точностью. При явной слабости (need ≈ 1) новый материал уступает закреплению, при лёгкой (need ≈ 0,2) почти не теряет в балле. Это прямо реализует пример из ТЗ: «если пользователь регулярно допускает ошибки… система рекомендует дополнительные упражнения; если результаты улучшаются — более сложные задания». Тест модуля ждёт так же, но только по темам своего модуля: пересдавать тест, пока его тема провалена, бессмысленно.
- **Давление прогресса** (`progression`: grace = 2 дня, full = 7 дней). Если новый урок не проходился дольше 2 дней, у следующего урока растёт признак `urgency` и к 7 дням достигает 0,5. Порог освоения не может бесконечно задерживать продвижение по пути.

## Сложность заданий

Целевая сложность (1–3) определяется по точности последних 30 ответов (нужно минимум 10): ниже 60% — «снижена», выше 85% — «повышена». Она используется в двух местах:

- при подборе упражнений для практики: выбираются задания со сложностью, ближайшей к целевой;
- в ранжировании: при повышенной сложности новый урок получает бонус и причину «Последние ответы точны на 92% — можно брать задания сложнее», при сниженной уступает место закреплению.

## План дня

`composePlan()` собирает план из рекомендаций так, чтобы он укладывался в бюджет времени:

1. Сначала входной тест, продолжение незавершённого и повторение слов. На повторение отводится не больше половины бюджета (`config.plan.reviewShare`), и число карточек (`target.reviewCount`) уменьшается вместе со временем. До rules-1.4 минуты урезались, а число карточек оставалось прежним, и пункт плана «повторение» обещал больше, чем помещалось.
2. Затем остальные рекомендации по убыванию балла. Занятие, которое не помещается в оставшееся время, пропускается, но более короткие ниже по списку ещё могут войти. В день допускается не больше 2 практик слабых тем, 2 «освежающих» практик и 1 повторного прохождения урока (`config.plan.remedialLimit`).
3. Хотя бы одно учебное занятие (не повторение) входит в план всегда. Поэтому при бюджете 10 минут план может превысить его на 1–3 минуты.

Порядок «урок или закрепление» план сам не выбирает: он следует баллам. Слабая тема получает место в плане потому, что порог освоения опускает балл нового урока ниже балла практики.

План фиксируется на календарный день пользователя (`dailyplans`). Отметки «выполнено» вычисляются по фактическим попыткам и повторениям, а кнопка «Пересобрать план» строит план заново по свежим данным.

## Интервальное повторение (упрощённый SM-2)

Состояние слова: ease factor (EF), интервал, число повторений, число «забываний», дата повторения. Оценка качества ответа q ∈ 0..5:

| Источник | q |
|---|---|
| Карточка: «Не помню / Трудно / Помню / Легко» | 1 / 3 / 4 / 5 |
| Ввод слова: верно быстрее 8 с / верно / почти верно / неверно | 5 / 4 / 3 / 1 |
| Выбор перевода: верно / неверно (узнавание проще воспроизведения) | 4 / 1 |

Правила:

- q ≥ 3: интервалы 1 → 6 → round(интервал·EF), где EF' = EF + 0,1 − (5 − q)(0,08 + 0,02(5 − q)), но не ниже 1,3.
- q < 3: повторения сбрасываются, интервал становится 1 день, число забываний растёт.

Три задокументированных отступления от классического SM-2:

1. Повторные неудачи по ещё не выученному слову не снижают EF. Это защищает от «ада коротких интервалов».
2. Если просроченное слово вспомнено уверенно (q ≥ 4), к прошлому интервалу добавляется половина срока просрочки.
3. Сроки выравниваются по началу локального дня пользователя. Часовой пояс хранится в профиле, расчёт выполняет `luxon`.

Новые слова попадают в повторение после завершения урока с первым сроком «завтра». В день вводится не больше 15 новых слов, сессия ограничена 20 карточками. Первыми идут слова с наибольшей относительной просрочкой. Слово, забытое 4 раза и более, получает статус «трудное» и показывается в режиме карточки с примером.

## Оценка качества

### Модульные сценарии

`test/unit/engine.test.ts` проверяет 29 сценариев, среди них:

- новому учащемуся предлагается входной тест, затем первый урок;
- слабая тема ранжируется выше нового урока и объясняется;
- тема без достаточных данных не считается слабой;
- после улучшения тема перестаёт рекомендоваться;
- падение результатов замечается даже при приемлемой средней точности;
- при высокой точности сложность повышается, при низкой — снижается;
- после перерыва первым идёт просроченное повторение;
- тест модуля предлагается, пока не сдан;
- переход на уровень предлагается после прохождения уровня;
- учитываются цели и игнорирование;
- результат детерминирован, веса настраиваются;
- план укладывается в бюджет;
- давно не практиковавшаяся тема считается возможно забытой (`topic_refresh`);
- явная слабость отодвигает новый урок, лёгкая — нет; тест модуля ждёт, пока слабы его темы;
- после нескольких дней без нового урока он снова поднимается в ранжировании;
- обнаруженная слабая тема попадает в план дня при бюджете 10, 15 и 20 минут.

`test/unit/evaluation.test.ts` дополнительно проверяет, что на профилях «grammar-struggler» и «irregular-forgetful» движок превосходит случайную стратегию по покрытию слабых мест, минимальному умению и удержанию слов, а «grammar-struggler» проходит в среднем не меньше 7,5 урока из 8.

### Симуляция синтетических учащихся

`npm run evaluate` моделирует 5 профилей учащихся на протяжении 30 дней по 50 прогонов. У каждого учащегося есть скрытое умение по темам, которое растёт при практике и снижается без неё. Стратегии видят только ответы. Сравниваются три стратегии:

- `engine` — движок вместе с планом дня;
- `sequential` — строго по порядку уроков, без повторения и практики;
- `random` — случайный выбор из того же пула кандидатов, что формирует движок.

Последние результаты лежат в [`evaluation-results.md`](evaluation-results.md).

#### Почему rules-1.3 проигрывал случайной стратегии

В rules-1.3 движок уступал `random` по покрытию слабых мест (25% против 43% у «grammar-struggler», 13% против 40% у «steady-average») и по минимальному умению. Разбор по дням (в какие дни самая слабая тема не попадала в план и почему) показал три причины в самом движке:

1. **Модель не учитывала забывание.** Тема, по которой неделями не было ответов, сохраняла последнюю хорошую оценку. В симуляции она забывается и часто становится самой слабой, но движок её не видел: «освежающая» практика включалась только через 10 дней и с баллом около 0,1, поэтому всегда проигрывала. Исправлено оценкой освоения с забыванием (см. выше). Абляция: без неё покрытие у «grammar-struggler» падает с 72% до 41%.
2. **Новый урок всегда опережал закрепление.** Балл урока (0,9) выше балла типичной слабой темы (0,75–0,85), а урок на 10 минут вместе с повторением занимал почти весь бюджет, и практика слабой темы (6 минут) уже не помещалась. Пока уроки не кончались, слабые места не закреплялись. Исправлено порогом освоения. Чтобы он не остановил продвижение, добавлено давление прогресса.
3. **«Освежение» занимало одно место и имело меньший prior**, поэтому из нескольких давно не практиковавшихся тем в план попадала не самая слабая. Теперь лимит — 2, а prior тот же, что у слабой темы (0,15): при равной потребности тип не важен.

Сама модель тоже исправлена в двух местах. Ни то, ни другое не подстраивает её под движок:

- **Знаменатель покрытия.** Метрика описана как «доля дней *с занятиями*», а в знаменатель попадали все дни, включая дни без занятий. В такой день покрыть слабую тему не может ни одна стратегия. Ошибка занижала числа всех стратегий, сильнее всего у нерегулярного учащегося. Теперь считаются только дни с занятиями. Для rules-1.3 покрытие у «grammar-struggler» стало 32% вместо 25%, у random — 53% вместо 43%: отставание осталось.
- **Одинаковый бюджет времени.** Раньше занятия выполнялись, пока бюджет не исчерпан, и последнее могло выйти за него. Движок обязан укладываться в бюджет, а случайная стратегия — нет, поэтому она занималась больше: 428 минут против 387 у «grammar-struggler», 343 против 304 у «short-sessions». Теперь ко всем стратегиям применяется правило `composePlan`. На сам rules-1.3 это почти не влияет: его покрытие 32,2% против 32,0%. Чтобы ничего не скрывать, в `evaluation-results.md` есть таблица и по прежнему правилу.

Ещё два изменения повышают точность модели и тоже касаются всех стратегий одинаково: в снимок добавлено `completedAt` урока, как в `LessonProgress`; повторение заканчивается на `reviewCount` карточек, как в продукте (пункт плана считается выполненным, когда повторено `reviewCount` слов).

Выводы:

- На профилях со слабыми местами («grammar-struggler», «irregular-forgetful», «short-sessions») движок теперь лучше обеих базовых стратегий и по минимальному умению, и по покрытию слабых мест. Удержание слов у него при этом в 1,5–3,5 раза выше, чем у `random`, потому что повторение слов всегда стоит в плане первым. Среднее умение не хуже, чем у `random`.
- У сильного учащегося слабых мест нет: все стратегии на 100% покрытия, а движок и `random` практически равны.

#### Оставшиеся слабые места (честно)

- **Цена закрепления — темп.** У «short-sessions» (10 мин) за 30 дней проходится 6,2 урока из 8 вместо 8 в rules-1.3. У «irregular-forgetful» — 4,3 вместо 5,8. При 10 минутах в день урок и практика в один день не помещаются, и движок чаще выбирает закрепление. Этот компромисс настраивается параметрами `remedialGate` и `progression`. Абляция показывает обе стороны: без порога освоения «short-sessions» проходит 7,9 урока при покрытии 30%, без давления прогресса — 5,5 урока при покрытии 55%.
- **«steady-average»: покрытие ниже, чем у random** (58% против 76%, у обоих разброс ±30 п. п.). У этого профиля выраженных слабых мест нет: все темы держатся около 60%, и «самая слабая» меняется почти каждый день. Движок, который видит только ответы, выбирает её не точнее случайности. По минимальному умению движок при этом не хуже. Сама метрика жёсткая: засчитывается только практика именно самой слабой темы, а не «одной из слабых».
- **При прежнем («мягком») правиле бюджета**, когда `random` получает на 25–40% больше времени, он обходит движок по минимальному умению у «grammar-struggler» и «steady-average». По покрытию у «grammar-struggler» и «irregular-forgetful» движок всё равно впереди.
- Параметры забывания (halfLife = 7 дней) и порога подобраны на этой же симуляции. Устойчивость к их выбору показана абляцией (halfLife = 14 дней), но её нужно проверить на реальных данных.

Ограничения оценки: учащиеся синтетические, параметры модели обучения выбраны вручную, поэтому результаты описывают поведение алгоритма, а не реальную эффективность обучения. Для реальной проверки нужен A/B-эксперимент с людьми.

## Расширение методами машинного обучения

- Функцию `recommend(snapshot)` можно заменить моделью с той же сигнатурой. Признаки (`features`) уже сохраняются в каждом снимке, а `followedKeys` фиксирует, какие рекомендации приняты. Получается готовый журнал для обучения ранжирования (learning-to-rank) или контекстного бандита.
- Для повторения слов в `reviewlogs` хранятся интервалы, качество ответов и просрочка. Этого достаточно для обучения half-life regression или FSRS вместо SM-2.
- Симулятор (`evaluation/simulator.ts`) подходит для подбора весов по сетке до A/B-теста.
