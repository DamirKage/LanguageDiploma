# Персонализация: рекомендации и интервальное повторение

## Общая схема

```
данные MongoDB ──► buildSnapshot() ──► LearnerSnapshot ──► recommend() ──► RecommendationResult ──► composePlan() ──► план дня
                     (service.ts)        (чистые данные)     (engine.ts)                               (plan.ts)
```

`recommend()` — чистая детерминированная функция. Она не обращается к базе данных и времени системы, поэтому её можно тестировать модульно, запускать в симуляции и заменить обученной моделью с той же сигнатурой. Версия движка (`ENGINE_VERSION`) сохраняется в каждом снимке рекомендаций (`recommendationsnapshots`).

## Входные данные (LearnerSnapshot)

| Сигнал | Источник | Как используется |
|---|---|---|
| Точность по темам | `answerevents`, только первые попытки; «почти верно» = 0,7 | Слабые темы, снижение результатов |
| Текущая точность | последние 12 ответов по теме (`recentWindow`) | Замечает улучшение, а не только историю |
| Результаты по сессиям | точность по теме в каждой попытке (≥ 2 ответов) | Признак падения результатов |
| Частые категории ошибок | ошибки по теме за 30 дней | Причина «повторяются ошибки категории …» |
| Прогресс уроков | `lessonprogresses` | Следующий урок, повторное прохождение |
| Незавершённые попытки | `attempts` со статусом `in_progress` | «Продолжить» |
| Итоговые тесты | завершённые попытки `kind=test` | Тест модуля, переход на уровень |
| Повторение слов | `reviewitems`, `reviewlogs` | Нагрузка, просрочка, удержание за 30 дней |
| Регулярность | `users.lastActiveAt` | Возвращение после перерыва |
| Недавняя точность | последние 30 ответов | Целевая сложность заданий |
| Цели и бюджет времени | профиль | Совпадение с целью, план дня |
| Игнорирование | снимки за 7 дней, кроме сегодняшнего | Мягкое снижение балла |

## Кандидаты и признаки

Каждый признак нормирован в [0, 1]. Балл кандидата:

```
score = prior[type] + w_need·need + w_urgency·urgency + w_progress·progress
      + w_momentum·momentum + w_trend·trend + w_goal·goal − w_fatigue·min(3, ignored)
```

Веса по умолчанию (`config.ts`): need 1.0, urgency 0.9, progress 0.7, momentum 0.8, trend 0.35, goal 0.15, fatigue 0.08.

| Тип | Условие | Признаки |
|---|---|---|
| `placement` | уровень не определён и нет прогресса | progress = 1, prior 1.5 |
| `resume` | есть начатая попытка не старше 14 дней | momentum = (0,5 + 0,5·доля выполненного)·свежесть |
| `review` | есть слова к повторению | urgency = 0,5·min(1, нагрузка/20) + 0,3·min(1, просрочка/7) + 0,2·перерыв; need при удержании < 80% |
| `weak_topic` | сглаженная текущая точность < 0,7 или падение ≥ 15 п. п. | need = clamp((0,85 − точность)/0,4), trend, urgency, goal |
| `topic_refresh` | тема не встречалась ≥ 10 дней | urgency = 1 − 2^(−(дни − 9)/14) |
| `next_lesson` | первый непройденный урок пути, начиная с уровня учащегося | progress: 1; 0,55 при сниженной сложности и наличии слабых тем; 1,2 при повышенной; ×0,8 после перерыва |
| `retry_lesson` | лучший результат урока < 70% | need = clamp((70 − лучший)/50 + 0,2) |
| `module_test` | все уроки модуля пройдены, тест не сдан | progress 0,8 |
| `level_up` | пройдены все уроки и тесты уровня | progress 1 |

Точность сглаживается байесовски: `(верно + 0,75·3) / (ответов + 3)`. При малом числе ответов оценка тянется к априорным 75%. Тема не считается слабой, пока по ней нет минимум 4 ответов (`minEvidence`). Так система разделяет наблюдаемые данные и оценки и не делает выводов по 1–2 ответам.

После ранжирования действуют ограничения разнообразия: не больше 2 слабых тем, по одному кандидату остальных типов, всего не больше 6 рекомендаций.

## Сложность заданий

Целевая сложность (1–3) определяется по точности последних 30 ответов (нужно минимум 10): ниже 60% — «снижена», выше 85% — «повышена». Она используется в двух местах:

- при подборе упражнений для практики: выбираются задания со сложностью, ближайшей к целевой;
- в ранжировании: при повышенной сложности новый урок получает бонус и причину «Последние ответы точны на 92% — можно брать задания сложнее», при сниженной уступает место закреплению.

## План дня

`composePlan()` собирает план из рекомендаций так, чтобы он укладывался в бюджет времени:

1. Сначала входной тест, продолжение незавершённого и повторение слов. На повторение отводится не больше половины бюджета.
2. Затем остальные рекомендации по убыванию балла, пока хватает времени. В день допускается не больше 2 практик слабых тем и по одной «освежающей» практике и повторному прохождению урока.
3. Хотя бы одно учебное занятие (не повторение) входит в план всегда.

План фиксируется на календарный день пользователя (`dailyplans`). Отметки «выполнено» вычисляются по фактическим попыткам и повторениям, а кнопка «Пересобрать план» строит план заново по свежим данным.

## Интервальное повторение (упрощённый SM-2)

Состояние слова: ease factor (EF), интервал, число повторений, число «забываний», дата повторения. Оценка качества ответа q ∈ 0..5:

| Источник | q |
|---|---|
| Карточка: «Не помню / Трудно / Помню / Легко» | 1 / 3 / 4 / 5 |
| Ввод слова: верно быстрее 8 с / верно / почти верно / неверно | 5 / 4 / 3 / 1 |
| Выбор перевода: верно / неверно (узнавание проще воспроизведения) | 4 / 1 |

Правила:

- q ≥ 3: интервалы 1 → 6 → round(интервал·EF), где EF' = EF + 0,1 − (5 − q)(0,08 + 0,02(5 − q)), но не ниже 1,3.
- q < 3: повторения сбрасываются, интервал становится 1 день, число забываний растёт.

Три задокументированных отступления от классического SM-2:

1. Повторные неудачи по ещё не выученному слову не снижают EF. Это защищает от «ада коротких интервалов».
2. Если просроченное слово вспомнено уверенно (q ≥ 4), к прошлому интервалу добавляется половина срока просрочки.
3. Сроки выравниваются по началу локального дня пользователя. Часовой пояс хранится в профиле, расчёт выполняет `luxon`.

Новые слова попадают в повторение после завершения урока с первым сроком «завтра». В день вводится не больше 15 новых слов, сессия ограничена 20 карточками. Первыми идут слова с наибольшей относительной просрочкой. Слово, забытое 4 раза и более, получает статус «трудное» и показывается в режиме карточки с примером.

## Оценка качества

### Модульные сценарии

`test/unit/engine.test.ts` проверяет 23 сценария, среди них:

- новому учащемуся предлагается входной тест, затем первый урок;
- слабая тема ранжируется выше нового урока и объясняется;
- тема без достаточных данных не считается слабой;
- после улучшения тема перестаёт рекомендоваться;
- падение результатов замечается даже при приемлемой средней точности;
- при высокой точности сложность повышается, при низкой — снижается;
- после перерыва первым идёт просроченное повторение;
- тест модуля предлагается, пока не сдан;
- переход на уровень предлагается после прохождения уровня;
- учитываются цели и игнорирование;
- результат детерминирован, веса настраиваются;
- план укладывается в бюджет.

### Симуляция синтетических учащихся

`npm run evaluate` моделирует 5 профилей учащихся на протяжении 30 дней по 50 прогонов. У каждого учащегося есть скрытое умение по темам, которое растёт при практике и снижается без неё. Стратегии видят только ответы. Сравниваются три стратегии:

- `engine` — движок вместе с планом дня;
- `sequential` — строго по порядку уроков, без повторения и практики;
- `random` — случайный выбор из того же пула кандидатов, что формирует движок.

Последние результаты лежат в [`evaluation-results.md`](evaluation-results.md). Главные выводы:

- Движок заметно превосходит последовательную стратегию по среднему и минимальному умению, покрытию слабых мест и удержанию слов. У последовательной стратегии удержание слов около 0%, потому что она их не повторяет.
- По сравнению со случайным выбором из того же пула движок даёт сопоставимое среднее умение и лучшее удержание слов. Покрытие самой слабой темы у него ниже, особенно при коротких сессиях (10 мин): там движок тратит время на новый урок, а практика в модели эффективнее урока. Отчасти это следует из предпосылок модели: практика в ней даёт в 1,6 раза больший прирост. Отчасти это ограничение ручных весов.
- Первая версия симуляции выявила реальные дефекты, которые были исправлены (версия движка `rules-1.2` → `rules-1.3`):
  - точность по теме считалась за всю историю, поэтому восстановившаяся тема оставалась «слабой»; теперь используется окно последних 12 ответов;
  - порог доказательности 6 ответов откладывал обнаружение новой слабой темы; теперь он равен 4 при байесовском сглаживании;
  - в план попадала только одна практика слабой темы; теперь до двух.

  Покрытие слабых мест у профиля «grammar-struggler» выросло с 17% до 25%.

Ограничения оценки: учащиеся синтетические, параметры модели обучения выбраны вручную, поэтому результаты описывают поведение алгоритма, а не реальную эффективность обучения. Для реальной проверки нужен A/B-эксперимент с людьми.

## Расширение методами машинного обучения

- Функцию `recommend(snapshot)` можно заменить моделью с той же сигнатурой. Признаки (`features`) уже сохраняются в каждом снимке, а `followedKeys` фиксирует, какие рекомендации приняты. Получается готовый журнал для обучения ранжирования (learning-to-rank) или контекстного бандита.
- Для повторения слов в `reviewlogs` хранятся интервалы, качество ответов и просрочка. Этого достаточно для обучения half-life regression или FSRS вместо SM-2.
- Симулятор (`evaluation/simulator.ts`) подходит для подбора весов по сетке до A/B-теста.
