# Нагрузочное тестирование

Вопрос: сколько учащихся одновременно выдержит один сервер и что ограничивает рост.

## Как проверялось

Сценарий `tools/load/scenario.mjs` имитирует учащихся через настоящий API, а не отдельные запросы. Каждый виртуальный учащийся регистрируется, выбирает язык и уровень, а затем по кругу выполняет занятие:

1. открывает «Сегодня» (план на день);
2. открывает программу курса и теорию урока;
3. начинает урок и отвечает на все задания;
4. завершает урок;
5. смотрит рекомендации, очередь повторения и сводку прогресса.

Между действиями делается пауза: в среднем 5 секунд, случайно от 2,5 до 7,5. Так ведёт себя человек, который читает задание и отвечает. Начало занятий разнесено во времени, чтобы все не нажимали кнопку в одну секунду.

```bash
# сервер в рабочем режиме, ограничение частоты отключено: генератор нагрузки работает с одного адреса
WEB_CONCURRENCY=3 RATE_LIMIT_ENABLED=false NODE_ENV=production node server/dist/index.js
node tools/load/scenario.mjs --url http://localhost:4000 --users 1000 --duration 90 --think 5
```

**Стенд:** одна виртуальная машина, 4 ядра, 16 ГБ памяти. На ней одновременно работали MongoDB 7, сервер и сам генератор нагрузки, поэтому результаты занижены по сравнению с раздельным размещением. В базе около 10 тысяч учётных записей и все 105 уроков.

## Что мешало и что исправлено

Профилирование под нагрузкой (`node --cpu-prof`, профилировщик MongoDB) показало четыре узких места.

| Проблема | Доля процессора до исправления | Исправление |
|---|---|---|
| Хеширование паролей (bcrypt) на основном потоке: каждый вход останавливал все остальные запросы примерно на 0,25 с | 34% | Пул рабочих потоков (`server/src/lib/password.ts`); основной поток свободен |
| Структура курса читалась из базы на каждый запрос плана, программы и рекомендаций | большая часть работы MongoDB | Кэш в памяти на 60 с, сбрасывается при любом изменении содержимого в админ-панели |
| План на день считал рекомендации дважды; пять отдельных проходов по истории ответов | — | Расчёт переиспользуется; один проход по истории (`$facet`) |
| Node.js использует одно ядро | один процесс загружен на 100%, машина наполовину простаивает | Кластерный режим: `WEB_CONCURRENCY=N` или `auto` запускает N процессов на одном порту |

Попутно исправлены две проблемы, найденные при разборе:

- **Сравнение пароля для несуществующего адреса** шло с меньшей стоимостью хеша, поэтому ответ приходил быстрее. По времени ответа можно было узнать, зарегистрирован ли адрес. Теперь стоимость одинаковая.
- **Ограничение частоты запросов считалось по IP-адресу.** Школа или университет выходят в интернет через один адрес, и класс из 30 человек упирался бы в лимит. Теперь ограничение считается так:
  - для вошедших — на учащегося;
  - для входа — на учётную запись: 30 попыток за 15 минут, плюс общий потолок 600 запросов на адрес.

  Это проверяется тестом «весь класс входит с одного адреса, а подбор пароля к одной учётной записи останавливается».

## Результаты

### Пропускная способность (без пауз, предельная нагрузка)

| Конфигурация | Запросов в секунду | p95 задержки |
|---|---|---|
| 1 процесс, до исправлений | 147 | 834 мс |
| 1 процесс, после исправлений | 223 | 452 мс |
| 3 процесса (кластер) | 402 | 508 мс |

### Учащиеся, занимающиеся одновременно (пауза 5 с, 3 процесса)

| Учащихся онлайн | Запросов в секунду | p50 | p95 | p99 | Ошибок |
|---|---|---|---|---|---|
| 1000 | 199 | 7 мс | 42 мс | 81 мс | 0 |
| 1500 | 271 | 10 мс | 2,0 с | 4,1 с | 0 |
| 2000 | 341 | 12 мс | 3,2 с | 9,2 с | 0 |
| 3000 | 382 | 375 мс | 5,9 с | 24 с | 0 |

p50, p95 и p99 — время, быстрее которого обработаны 50%, 95% и 99% запросов. Время ответа сервера до 100 мс человек воспринимает как мгновенное.

## Вывод

- **Один сервер с 4 ядрами выдерживает 1000 учащихся, занимающихся в одну и ту же минуту.** 95% ответов приходят быстрее 0,05 с, ошибок нет.
- **На 1500–3000 одновременных учащихся сервер не отказывает,** ни одной ошибки, но отдельные запросы ждут секунды. Процессор машины занят полностью: MongoDB около 1,2 ядра, три процесса сервера около 2,1, генератор около 0,3.
- **Зарегистрированных пользователей может быть намного больше, чем одновременно занимающихся.** Обычно в одну минуту занимается 5–15% зарегистрированных. Для 1000–2000 зарегистрированных это 50–300 человек: такая нагрузка в разы ниже проверенной.

Как расти дальше без изменения кода:

1. **Вынести MongoDB на отдельную машину** или в управляемый сервис. Это освобождает больше ядра для сервера.
2. **Запустить несколько копий сервера за балансировщиком** (nginx). Сервер не хранит сессий в памяти: вход работает на JWT, а токены обновления лежат в базе.
3. **Для многосерверной установки** перенести счётчики ограничения частоты в общее хранилище, например Redis. Сейчас каждый процесс считает их сам, поэтому фактический лимит умножается на число процессов. Изменения курса другие копии сервера видят через 60 секунд (время жизни кэша).

## Ограничения проверки

- Генератор нагрузки и база работали на той же машине, что и сервер.
- Статические файлы (страницы, аудио) отдаёт веб-сервер или CDN, они в тест не входили.
- Сеть локальная, без задержек интернета.
- Сценарий один: прохождение урока. Админ-панель не нагружалась.
